# Sub-Zero Development Rules

Version: 1.0

Purpose:

This document defines the engineering principles, architectural rules, and implementation guidelines for the Sub-Zero project.

Every new feature, refactor, bug fix, and AI-generated implementation must comply with these rules.

If any implementation conflicts with these rules, the implementation must be revised rather than changing the architecture.

---

# 1. Core Principles

## 1.1 Single Source of Truth

All business logic must have exactly one owner.

Examples:

- Income Matching → Income Engine
- Cash Flow Calculations → Cash Flow Engine
- Transaction Parsing → Transaction Parser
- Gmail Synchronization → Gmail Sync Service
- Notifications → Notification Service

No business logic may exist in multiple locations.

---

## 1.2 Backend Owns Business Logic

The Node.js backend is the only source of financial calculations.

Flutter is responsible only for:

- Rendering UI
- User interaction
- API communication
- Local caching for offline viewing
- Theme & preferences

Flutter must never calculate:

- Income
- Goal Progress
- Budget Usage
- Cash Flow
- Financial Health Score
- Transaction Classification

---

## 1.3 MongoDB is the Single Source of Truth

Financial state must always come from MongoDB.

Never rely on:

- SharedPreferences
- Cached calculations
- Local financial state

Local storage is allowed only for:

- Theme
- User preferences
- Cached API responses
- Offline support

---

# 2. Transaction Pipeline

Every Gmail email must pass through exactly the following pipeline.

Gmail

↓

Incremental Sync

↓

Transaction Validation

↓

Transaction Parser

↓

Merchant Extraction

↓

Category Engine

↓

Income Engine

↓

Cash Flow Engine

↓

MongoDB

↓

Notification Engine

↓

Frontend

No stage may be skipped.

No component may perform responsibilities belonging to another stage.

---

# 3. Domain Ownership

Each business domain has exactly one owner.

| Domain | Owner |
|---------|-------|
| Gmail Sync | GmailSyncService |
| Transaction Validation | TransactionValidationEngine |
| Transaction Parsing | TransactionParser |
| Merchant Extraction | MerchantExtractor |
| Category Classification | CategoryEngine |
| Income Detection | IncomeEngine |
| Income Cycles | CashFlowEngine |
| Goal Allocation | CashFlowEngine |
| Budget Tracking | CashFlowEngine |
| Overspending Detection | CashFlowEngine |
| Financial Health Score | FinancialHealthEngine |
| Notifications | NotificationService |

No duplicate ownership is permitted.

---

# 4. Service Rules

Each service must have a single responsibility.

Services must never:

- Duplicate another service
- Perform unrelated work
- Access UI logic
- Modify another service's internal state

If a service begins performing multiple unrelated responsibilities, it must be split.

---

# 5. Database Rules

MongoDB is the only persistent datastore.

Collections must be owned by one domain.

Every collection must have:

- Purpose
- Owner
- Read path
- Write path

No collection may exist without a documented owner.

---

# 6. API Rules

All communication between Flutter and backend must occur through REST APIs.

Flutter never directly manipulates MongoDB.

Business logic must never depend on Flutter.

API responses should return processed data rather than requiring Flutter to perform calculations.

---

# 7. Cash Flow Rules

The Cash Flow Engine owns:

- Income Cycles
- Goal Allocation
- Category Budgets
- Remaining Available Income
- Budget Usage
- Overspending Detection
- Monthly Reconciliation

No other service may calculate these values.

---

# 8. Income Rules

Income Sources are user-defined recurring income configurations.

Income Cycles represent actual confirmed income for a specific period.

Configured Income and Confirmed Income are different concepts.

Only one confirmed income transaction is allowed per Income Source per Income Cycle.

---

# 9. Budget Rules

Budgets are virtual spending limits.

Budgets never move actual money.

Budget calculations are always derived from categorized transactions.

Budget usage is recalculated whenever:

- Transactions change
- Categories change
- Budgets change

---

# 10. Goal Rules

Savings Goals represent virtual allocations.

They do not represent actual bank balances.

Goal balances are calculated from confirmed Income Cycles.

Money is never assumed to remain in a goal after spending.

Overspending reconciliation requires user confirmation.

---

# 11. Notification Rules

Notifications are event-driven.

They must never calculate business logic.

They only react to events generated by backend services.

Examples:

- Income Confirmed
- Goal Completed
- Budget Threshold Reached
- Overspending Detected

---

# 12. Logging Rules

Every major backend stage must use structured logging.

Required levels:

INFO

WARN

ERROR

DEBUG

Logs must include:

- User ID
- Transaction ID
- Gmail Message ID (if applicable)
- Income Cycle ID (if applicable)
- Timestamp
- Processing stage

---

# 13. Error Handling

No silent failures.

Every failed stage must:

- Log the reason
- Return meaningful errors
- Avoid partial financial updates

Financial operations should be atomic whenever possible.

---

# 14. AI Development Rules

Every AI implementation must:

- Follow the approved architecture.
- Reuse existing services whenever possible.
- Never introduce duplicate logic.
- Never create undocumented collections.
- Never create undocumented APIs.
- Never bypass the transaction pipeline.
- Explain any required architectural changes before implementation.

---

# 15. Code Quality Rules

Every new feature must include:

- Unit tests
- Integration tests (where applicable)
- Structured logging
- Error handling
- Documentation updates

---

# 16. Performance Rules

Never rescan the full Gmail inbox.

Always use incremental synchronization.

Avoid duplicate MongoDB queries.

Use indexes where appropriate.

Cache only non-financial data.

---

# 17. Security & Privacy Rules

Sub-Zero follows a Privacy-by-Design architecture.

Users' financial information is considered highly sensitive.

All components must minimize data collection, protect stored data, and prevent accidental exposure.

---

## 17.1 Data Classification

Every stored field must belong to one of the following classes:

### Public

Examples:

- Theme
- App settings
- Category colors
- Goal icons

Stored normally.

---

### Internal

Examples:

- Category names
- Budget values
- Goal progress
- Statistics

Stored normally.

---

### Sensitive

Examples:

- Merchant names
- Sender names
- Transaction descriptions
- Income sources
- Gmail Message IDs
- Transaction reference numbers
- User notes

Must be encrypted before storage.

---

### Critical

Examples:

- OAuth Access Tokens
- Refresh Tokens
- Session Tokens
- Gmail credentials
- API secrets

Must always be encrypted.

Never log these values.

Never expose them to the frontend.

---

## 17.2 Encryption

Sensitive data stored in MongoDB must be encrypted before persistence.

Recommended:

AES-256-GCM

Encryption must occur in the backend before writing to MongoDB.

Encryption keys must never be stored in source code.

Keys must be loaded from environment variables or a secure secret manager.

---

## 17.3 Passwords

Passwords must never be encrypted.

Passwords must be hashed using:

- Argon2id (preferred)
- bcrypt (acceptable)

Passwords must never be recoverable.

---

## 17.4 Tokens

OAuth tokens must:

- Be encrypted before storage.
- Never be returned by APIs.
- Never appear in logs.
- Never be cached on the frontend.

---

## 17.5 Transaction Privacy

Financial transaction data must never be sent to external AI services.

All parsing, categorization, and financial calculations must occur entirely within the Sub-Zero backend using deterministic logic.

No third-party service may receive:

- Merchant names
- Sender names
- Transaction descriptions
- Amounts
- Account details
- Budget data
- Goal data

unless explicitly approved by the user.

---

## 17.6 Logging

Logs must never contain:

- OAuth Tokens
- Refresh Tokens
- Email bodies
- Transaction descriptions
- Reference numbers
- Account numbers

Logs should instead contain:

- User ID
- Transaction ID
- Processing Stage
- Success/Failure
- Timestamp

Mask sensitive values whenever possible.

Example:

Account:
XXXX2860

UPI:
vikram****@okaxis

---

## 17.7 API Responses

Never expose encrypted fields directly.

Sensitive fields must be:

- decrypted by the backend only when required
- masked where appropriate
- returned only to the authenticated owner

---

## 17.8 MongoDB Storage Rules

Before writing to MongoDB:

- Validate input.
- Normalize values.
- Encrypt sensitive fields.
- Hash fields requiring one-way verification.
- Store only the minimum required information.

Never store duplicate sensitive data.

---

## 17.9 Frontend Storage

Flutter must never permanently store:

- OAuth tokens
- Gmail credentials
- Financial calculations
- Sensitive transaction metadata

Only cache non-sensitive data required for offline viewing.

Sensitive cached data must be encrypted using platform-secure storage.

---

## 17.10 Principle of Least Privilege

Every API endpoint, service, and database query should access only the minimum data required to complete its task.

Avoid returning entire MongoDB documents when only a subset of fields is needed.

---

## 17.11 AI Development Rule

Any new feature introducing a database field must specify:

- Data classification
- Storage method
- Encryption requirement
- API exposure
- Logging policy

No new field may be added until its privacy classification has been documented.

---

## Rules

Before adding any new MongoDB field, the following questions must be answered:

1. What is the field's privacy classification?
2. Should it be encrypted?
3. Should it be hashed?
4. Can it be returned through the API?
5. Should it appear in logs?
6. Does this field already exist elsewhere?
7. Is storing this field absolutely necessary?

If these questions cannot be answered, the field must not be implemented.

---

## Privacy Principle

Sub-Zero follows the principle of **Minimum Necessary Data**.

The system should:

- Store only the minimum data required.
- Encrypt all sensitive financial information before persistence.
- Never duplicate sensitive data.
- Never expose confidential data to third-party AI services.
- Never return unnecessary fields through APIs.
- Always prefer derived values over storing duplicate calculations.
- Mask sensitive information whenever displayed in the UI or logs.

---

## AI Implementation Requirement

Before generating database code, every AI implementation must produce a "Privacy Review" for any new collection or field.

The review must specify:

- Collection Name
- Field Name
- Data Classification
- Encryption Requirement
- API Exposure
- Logging Policy
- Justification for Storage

Database code must not be generated until this review has been completed.

---

# 18. Refactoring Rules

When implementing new features:

1. Search for an existing service before creating a new one.
2. Reuse existing collections.
3. Reuse existing APIs.
4. Preserve backwards compatibility where possible.
5. Update architecture documentation if responsibilities change.

---

# 19. Future Features

Every new feature must answer:

1. Which domain owns this?
2. Which service implements it?
3. Which MongoDB collection stores it?
4. Which API exposes it?
5. Which events does it generate?
6. Does it violate any Development Rule?

If any answer is unclear, implementation must stop until the architecture is updated.

---

# 20. Guiding Principle

Sub-Zero prioritizes:

Correctness > Simplicity > Performance > New Features

A feature must never compromise the consistency of the financial system.

The architecture is the source of truth.
The code must conform to the architecture—not the other way around.
